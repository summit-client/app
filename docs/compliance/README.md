# Compliance control layer

What is here, what it proves, and — more importantly — what it does not.

## The distinction this directory exists to hold

There are four different things people mean by "compliant", and conflating them
is how an organization ends up believing it is covered when it is not:

1. **Technical control implemented** — the code does the thing. This is what
   `supabase/tests/controls.mjs` demonstrates, on every CI run.
2. **Compliance readiness** — controls plus the organizational policies,
   agreements and processes that a framework requires. Partly here, mostly not.
3. **Organizational compliance** — the organization operates that way in
   practice, with evidence over time.
4. **Independently audited or certified** — an assessor has examined it and
   issued a report or certificate.

**This repository reaches level 1 and part of level 2. Nothing here is evidence
of 3 or 4.**

Do not describe this product as HIPAA compliant, SOC 2 compliant, SOC 2
certified, or ISO 27001 certified. The accurate phrasing is *"designed with
controls supporting…"* until the organization has determined otherwise on
evidence it can produce.

Note also that ISO 27001 certifies an organization's ISMS within a defined
scope, and SOC 2 attests to an organization's controls over a period. Neither
is something a codebase can hold.

## What is generated, and what is written by hand

Generated artefacts cannot go stale. Hand-written ones can, and this repository
has already produced three stale claims that were believed until re-derived: a
`CLAUDE.md` note calling `invite-teammate` unfixed after it was fixed, a "not
yet applied" comment on migration `0041` after it was applied, and a list of
admin-console queues described as broken after another session had wired them.

| Artefact | Source | Drifts? |
|---|---|---|
| `CONTROL_MATRIX.md` | generated by `supabase/tests/controls.mjs --matrix` | no |
| `DATA_INVENTORY.md` | generated by `supabase/tests/data-inventory.mjs --md` | no |
| `VENDOR_REGISTER.md` | hand-written, method recorded | **yes** |
| `THREAT_MODEL.md` | hand-written | **yes** |
| `DATA_RETENTION.md` | hand-written — retention is a legal decision | **yes** |

Regenerate the first two:

```bash
node supabase/tests/controls.mjs supabase/migrations --matrix > docs/compliance/CONTROL_MATRIX.md
node supabase/tests/data-inventory.mjs supabase/migrations --md > docs/compliance/DATA_INVENTORY.md
```

CI regenerates and diffs them, so a migration that changes the security posture
without updating the matrix fails the build.

## Running the controls

```bash
node supabase/tests/controls.mjs supabase/migrations
```

Exit 1 on any failure. Eleven automated controls, each a query against the
schema the migrations build; five manual controls listed with an owner and a
state rather than omitted.

**Each automated control has been mutation-tested** — a deliberate violation was
introduced and the control confirmed to catch it. A control that cannot fail is
not evidence, and a register where everything passes on the first run is
exactly when that matters most.

## What these controls do not cover

- **They run against a PGlite rebuild, not the live database.** A policy dropped
  by hand in the Supabase dashboard is invisible here. Verifying the live
  project is a separate, manual step.
- **`auth.uid()` is a stub** reading a session variable, not a real JWT. A policy
  depending on any other claim is not exercised.
- **Application-layer authorization** is covered by `supabase/tests/rls.mjs`
  (198 tests) and `behaviour.mjs` (69), not by the control register.
- **Nothing here tests the network, the host, TLS, backups, or the deploy
  pipeline.**
- **Classification in the data inventory is inferred from names.** It is a
  starting point for human review, deliberately biased toward over-classifying.

## Known open items

These are real and currently unmet. They are listed here rather than in a
tracker so that anyone reading the compliance directory sees them.

- **No Supabase BAA/DPA.** No real PHI may enter the system until this is
  signed. `docs/context/compliance.md` records it as gating revenue.
- **Azure OpenAI retention terms unverified.** Abuse monitoring retains prompts
  up to 30 days unless the zero-retention exemption is approved. Which applies
  has not been confirmed.
- **Sentry PII scrubbing unverified.** An error thrown inside a request handler
  can carry record contents; no scrubbing configuration is checked in.
- **MFA not enforced** for admin and supervisor roles — a Supabase Auth setting.
- **No restore has been rehearsed.** A backup that has never been restored
  should not be assumed to work.
- **No dependency vulnerability scanning or SAST in CI** beyond the secret and
  control gates added alongside this directory.
- **Data residency is mapped only partially.** The database region, AI
  processing region and email egress have not all been confirmed against a
  single commitment.

## The rule this directory is meant to enforce

Do not build a control that cannot later be demonstrated to an auditor. If a
control cannot be evidenced, it is a statement of intent — and statements of
intent belong in the open-items list above, not in the matrix.
